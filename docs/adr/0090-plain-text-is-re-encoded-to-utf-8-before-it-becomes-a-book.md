# Plain text is re-encoded to UTF-8 before it becomes a Book, and its id is the hash of the UTF-8

Unlike an EPUB or a Markdown file, a `.txt` file is not stored as received: the importer decodes it (UTF-8 with or without a byte-order mark, UTF-16 with a mark, otherwise GB18030, which covers GB2312 and GBK) and stores UTF-8 without a mark, so the browser reads it with no guessing. A Book's id is the SHA-256 of what is stored, so the same text saved in GBK, in UTF-8 and in UTF-8 with a mark is one Book, and a Reading position can never be stranded by re-saving a file in another encoding. The cost is that the stored bytes are not the file the user dropped in (the original is never touched; see "original file survives deletion"), and that the id is not the hash of the upload, so a format that rewrites its input does it in `BookFormat.normalize`, before the id is computed. Detection uses only Node's built-in `TextDecoder` (strict-enough UTF-8 first, since GBK text is almost never valid UTF-8, then GB18030), so no encoding-detection dependency is added; encodings it does not know (Big5, Shift-JIS, Windows-1252) are not recognised and are read as GB18030, which shows them as garbage rather than failing.
