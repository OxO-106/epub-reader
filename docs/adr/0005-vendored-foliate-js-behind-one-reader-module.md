# Vendor foliate-js behind a single Reader module

foliate-js renders every Book, but it has no releases and its README warns that the API will break, so we keep a pinned copy of only the files we use in `src/web/vendor/foliate-js` and let exactly one file, `src/web/reader/reader.ts`, import it at runtime (type-only imports of the vendored typings, which compile to nothing, are allowed elsewhere, as `custom-book.ts` does). The rest of the app sees a small `Reader` interface (open, go to, next, previous, location events), which is also where Markdown and plain-text Books plug in as a custom book object. We chose this over an npm dependency (nothing to pin to) and over using foliate-js directly in components (an upstream change would ripple through every screen). The cost is that updating foliate-js is a manual copy and re-test, and the Reader module builds the EPUB itself (with our own SHA-1 for font de-obfuscation) instead of calling foliate-js's file opener. Because the EPUB pages run in same-origin iframes, the server's Content-Security-Policy (`src/server/security.ts`, scripts from `'self'` only) is a hard requirement of this decision: loosening it lets a Book's script run with the app's privileges.
